# Публикация Qipli

Правила именования и объём команд пользователя находятся в [AGENTS.md](../AGENTS.md). Технический контракт находится в [TECHNICAL.md](TECHNICAL.md#10-сборка-и-распространение), актуальные gates в [STATE.md](STATE.md). Этот документ описывает выполнение процесса, а не текущий статус релиза.

## 1. Проверить исходное состояние

1. Прочитать STATE и release gates выбранных срезов. Разделить обязательные проверки до публикации и проверки установленного опубликованного обновления. Непроверенные критерии остаются открытыми.
2. Проверить `git status --short`, текущую ветку, `git remote -v`, открытые PR и release runs. Сохранить чужую незавершённую работу; при необходимости использовать отдельный worktree. Не начинать второй выпуск параллельно уже идущей публикации.
3. Выполнить `git fetch origin --prune --tags`. Через GitHub проверить опубликованные версии, теги и build numbers, включая маркеры `<!-- qipli-build: N -->` в release notes. Локальные refs и STATE не заменяют эту проверку.
4. Зафиксировать выбранную версию и состав изменений относительно последнего опубликованного тега. Если номер версии не задан и его нельзя однозначно определить из согласованного состава, уточнить его до изменения версии.
5. Доставить выбранные изменения из `feature/<описание>` в `main` через PR в пределах полученной авторизации. Не включать посторонние изменения молча. Если состав `main` не соответствует согласованному выпуску, сначала разрешить расхождение.

## 2. Подготовить версию

Создать `release/X.Y.Z` от свежего `origin/main`. Если ветка уже существует, проверить её базу и diff и продолжить подготовку; не пересоздавать и не сбрасывать её автоматически.

В одном PR `Release X.Y.Z` подготовить:

- `Config/Version.xcconfig`: `MARKETING_VERSION = X.Y.Z`, `CURRENT_PROJECT_VERSION` строго больше максимального опубликованного build number;
- `docs/release-notes-template.md`: изменения именно этого выпуска, актуальные требования, установка и ограничения. Publisher добавляет build marker и GitHub generated notes автоматически.

Функциональные изменения и найденные исправления проходят отдельный рабочий PR в `main`, после чего база релизного PR обновляется и проверки повторяются для изменённого кандидата. Исключение для существующей ветки 1.0.11 задано в AGENTS.md.

Минимальные локальные проверки подготовки:

```sh
scripts/tests/validate-version-tests.sh
scripts/check-project-version.sh
scripts/check-ci-contract.sh
scripts/tests/release-contract-tests.sh
git diff --check
```

Полный unsigned gate определён в `.github/workflows/ci.yml`: public-readiness audit, SwiftPM tests, Debug/Release builds и проверки metadata/runtime linking. Локальные проверки не заменяют CI.

При запросе только подготовки остановиться с локальным diff, результатами проверок и открытыми gates. При разрешённом PR закоммитить только относящиеся к нему файлы, выполнить push и создать PR в `main`. Приложить PR к задаче. Обычный push релизной ветки без PR не запускает текущий unsigned CI.

## 3. Слить и поставить тег

Этот этап выполняется при разрешённой публикации.

1. Дождаться успешных проверок PR и выполнения обязательных pre-release gates. Слить PR без обхода защиты `main`.
2. Обновить refs, определить точный SHA итогового коммита в `main` и дождаться успешного push-to-main CI именно для него. Не переносить успех PR CI на другой SHA.
3. Перепроверить version/build и итоговый состав на этом SHA. Если `main` продвинулся, не переключать выпуск автоматически на новый HEAD.
4. Убедиться, что тег `vX.Y.Z` отсутствует локально и на origin. Создать annotated tag на выбранном SHA. Если тег существует, разобрать состояние выпуска, не перемещать его.
5. В чистом detached worktree этого тега с актуальным `origin/main` выполнить `scripts/check-release-admission.sh vX.Y.Z`. Скрипт требует совпадения HEAD и тега, version/tag и принадлежности коммита `origin/main`.
6. Отправить только этот тег через `git push origin refs/tags/vX.Y.Z`. Не использовать `git push --tags`.

`X.Y.Z` в командах заменяется выбранной версией перед исполнением.

## 4. Дождаться публикации и проверить результат

Push тега запускает `.github/workflows/release.yml`. Signing и публикация выполняются через него. Protected `release` Environment может потребовать отдельного GitHub approval; сообщить пользователю ссылку и ожидающий шаг, не обходить защиту.

Workflow проверяет точный тег, выполняет tests/build, подписывает и notarize/staple приложение и DMG, создаёт подписанный Sparkle appcast. Publisher проверяет draft assets, публикует Release и повторно проверяет публичные файлы. Затем отдельный job развёртывает appcast в Pages.

После завершения проверить:

- Release публичен и имеет нужный тег, version/build и ожидаемый SHA;
- доступны `Qipli-X.Y.Z.zip`, `Qipli-X.Y.Z.zip.sha256`, `Qipli-X.Y.Z.dmg`, `Qipli-X.Y.Z.dmg.sha256` и `Qipli.dmg`; проверки скачанных файлов, подписи, notarization и Gatekeeper подтверждены workflow либо отдельной проверкой;
- job `deploy-appcast` успешен, публичный feed содержит нужные version/build, URL неизменяемого ZIP и Sparkle signature;
- проверки установленного обновления, сохранения данных и Accessibility выполнены либо явно остаются открытыми. Успешный workflow не доказывает clean-machine или installed-update acceptance.

Обновить STATE коротким результатом и следующим действием; подробное evidence хранить по существующим правилам документации. В ответе указать version/build, SHA/тег, ссылки на PR, workflow и Release, результаты DMG/ZIP/Sparkle и открытые gates.

## 5. Восстановление после сбоя

Перед повтором прочитать ошибку run и проверить фактическое состояние тега, Release и Pages. Не запускать повторную notarization вслепую.

- Если публикации ещё нет, причина устранена без изменения исходников тега и разрешение на публикацию сохраняется, использовать recovery `workflow_dispatch` существующего тега либо повтор нужного run. Не менять тег. Если нужны изменения кода или workflow, подготовить новый проверенный коммит и новую версию.
- Если Release уже публичен, publisher повторную публикацию отклонит. Не удалять Release, не заменять assets и не запускать весь pipeline заново ради Pages.
- Если упал только `deploy-appcast`, повторить этот job с уже загруженным verified Pages artifact. Если artifact недоступен или сбой произошёл между публикацией Release и загрузкой Pages artifact, зафиксировать частично завершённый выпуск и подготовить отдельное восстановление appcast из опубликованного ZIP с проверкой подписи. Готового отдельного recovery workflow для этого случая сейчас нет.
- Перед восстановлением старого appcast проверить, не опубликована ли более новая версия: восстановление не должно откатывать feed. Дефект опубликованного приложения исправляется новым выпуском.
